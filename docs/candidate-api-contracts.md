# Candidate API contracts and state/error semantics

**Base path:** `/api/v1`  
**Authentication:** Candidate routes require the configured authenticated principal. Candidate resource IDs are not authorization: services scope reads and writes to the authenticated user and return not-found for cross-candidate resources where tested. Admin routes are outside this candidate contract and require their own authorization rules.  
**Source of truth:** Runtime routes and Pydantic request/response schemas in `app/api/v1/`; generated OpenAPI is available from the FastAPI application. This document summarizes implemented contracts, not a promise that every possible provider/runtime failure has been exercised.

## Common response and error behavior

- Successful resource responses generally use `{"data": ...}`. Collection endpoints may return `{"data": [...], "pagination": {"limit": N, "offset": N, "total": N}}`; check the endpoint-specific table below because not every collection has the same envelope.
- Domain errors use HTTP status from the domain error and `{"error": {"code": "...", "message": "...", "details": {}, "request_id": ...}}`.
- Request validation errors use HTTP 422 and a `detail` array containing only stable `type`, `loc`, and `msg` fields. Submitted values are not echoed.
- Some route handlers deliberately raise FastAPI `HTTPException`; those responses use FastAPI's `detail` envelope rather than the domain-error envelope. Clients must use the HTTP status and the endpoint-specific response body, not assume all errors have one shape.
- Request IDs are attached by middleware and exposed through the `X-Request-ID` response header. Request body limit is 100,000 bytes; oversized requests return 413.
- Unknown request fields are rejected on contracts whose Pydantic models set `extra="forbid"`. Do not send client-controlled actor/source fields unless explicitly part of a request schema.

## Endpoint contract inventory

| Capability | Method and path | Contract highlights | State, error, and retry semantics |
|---|---|---|---|
| Candidate profile | `GET /candidate/profile`; `PATCH /candidate/profile`; `GET /candidate/profile/provenance` | Profile is resolved from the authenticated user; patch includes `expected_revision` and sections. | Stale revision returns 409 `REVISION_CONFLICT`; provenance records source and profile revision. |
| Evidence library | `POST /candidate/evidence`; `GET /candidate/evidence`; `GET/PATCH /candidate/evidence/{evidence_id}`; `POST /candidate/evidence/{evidence_id}/{submit,approve,reject,archive}` | Evidence list/detail is candidate-scoped; lifecycle actions accept an explicit transition payload. | Invalid/stale transitions are rejected; cross-candidate resource access is denied without returning the other candidate's content. |
| Candidate claims | `GET/POST /candidate/claims`; `PATCH /candidate/claims/{claim_id}`; `POST /candidate/claims/{claim_id}/{submit,approve,reject,archive}` | Claim transitions are explicit actions, not arbitrary status updates. | Transition rules and evidence/provenance checks remain authoritative in the service. |
| Preferences | `GET/PUT /candidate/preferences` | Versioned candidate-owned settings; update validates known fields and values. | Invalid input returns 422; revision conflicts return 409 where the expected revision is stale. |
| Career pathways | `GET/POST /candidate/career-pathways`; `POST /candidate/career-pathways/suggestions`; `GET/PATCH /candidate/career-pathways/{pathway_id}`; `POST /candidate/career-pathways/{pathway_id}/{approve,reject,retire}`; `GET /candidate/career-pathways/{pathway_id}/events` | AI suggestions remain pending until candidate decision; decision requests carry revision/reason fields. | Revision conflicts and invalid transitions are rejected; ownership and foreign evidence references are checked. |
| Document import | `POST /candidate/document-imports`; `POST /candidate/document-imports/{import_id}/{parse,extract-fields,identify-conflicts,confirm,save}`; `GET /candidate/document-imports`; `GET /candidate/document-imports/{import_id}`; `GET /candidate/document-imports/{import_id}/preview` | Import is preview/confirmation driven; history is candidate-scoped. | Parse/extraction/storage failures remain retryable where supported; failed or unconfirmed extraction must not become authoritative evidence; conflict decisions require explicit review. |
| Discovery settings/missions | `GET/PUT /candidate/discovery/settings`; `POST/GET /candidate/discovery/missions` | Settings are revisioned; mission creation accepts an idempotency key. | Invalid settings return 422; stale revisions return 409; mission replay with the same key is idempotent; failed source outcomes must not be reported as empty success. |
| Canonical Job Pool | `GET /candidate/jobs/pool`; `GET /candidate/jobs/pool/{job_id}` | List supports `limit` (default 20, range 1–50), `offset` (default 0), search and job filters. | Only publicly approved jobs are listed; private/manual submission provenance is not exposed as public source data. |
| Opportunities/evaluations | `GET /candidate/opportunities`; `POST /candidate/evaluations`; `GET /candidate/evaluations`; `GET /candidate/evaluations/{evaluation_id}`; `POST /candidate/evaluations/{evaluation_id}/overrides`; `GET /candidate/evaluations/{evaluation_id}/overrides` | Feed uses `limit` (default 20, range 1–50) and `offset`; evaluations persist decision provenance. | Stale jobs/evidence/rules/pathways/routes and deterministic hard blockers prevent unsafe qualification; overrides are revisioned and append-only. |
| Punts | `POST/GET /candidate/punts` | Punt creation rechecks current evaluation and job eligibility rather than trusting client claims. | Duplicate/concurrent qualification converges to one Punt; stale/cross-candidate evaluation is rejected. |
| Application tracking | `POST/GET /candidate/applications`; `POST /candidate/applications/{application_id}/transition`; `GET /candidate/applications/{application_id}/events` | Transition request uses `target_status`, `expected_revision`, required `reason`, optional `notes`. | See [application lifecycle contract](application-lifecycle.md) for the full allowed transition matrix. Invalid transitions and stale revisions leave state/event/outbox unchanged. Real-world milestones are candidate-recorded; creation is not employer submission. |
| CV Studio | `GET /candidate/cvs`; `POST /candidate/cvs/master/regenerate`; `POST /candidate/cvs/variants`; `GET /candidate/cvs/{cv_key}`; `POST /candidate/cvs/{cv_key}/versions`; `POST /candidate/cvs/{cv_key}/versions/{version_number}/approve`; document generation/download routes under the CV version | Versioned master/variant content; approval binds to an exact version. | Cross-candidate access and downloads of unapproved/foreign versions are denied. |
| Application packages | Routes under `/candidate/applications/{application_id}/packages`: create/list/get, revisions, claim validation, review preparation/decision, document generation/download. | Package revision snapshots job description, evaluation, evidence, CV version, artifacts and AI task provenance. | Stale/tampered provenance or unsupported claims fail readiness/review; candidate approval binds to the exact revision. |
| Notifications | `GET /candidate/notifications`; `POST /candidate/notifications/{notification_id}/read`; `GET/PUT /candidate/notifications/email-preferences` | Notification list supports `limit` (default 20, range 1–100), `offset`, and `unread_only`. Email preference defaults to disabled. | Read/list/preferences are candidate-scoped; opt-in requires verified email; delivery requires current consent and verification. Email retry is bounded by outbox policy. |
| Candidate support | `POST/GET /candidate/support/tickets`; `GET /candidate/support/tickets/{ticket_id}`; `POST /candidate/support/tickets/{ticket_id}/messages`; `PATCH /candidate/support/tickets/{ticket_id}/status` | Ticket/message create requests use an `idempotency_key`; ticket list supports `limit` (default 20, range 1–100), `offset`, `status`, and `unread_only`. | Same key + same payload returns existing resource; conflicting key reuse returns 409. Tickets resolve before closure; closed tickets are terminal and follow-up uses a linked ticket. See [support API contract](support-api.md). |

## Contract test evidence

The route inventory is guarded by `tests/unit/test_candidate_api_contract.py`, which checks critical candidate paths, methods, generated OpenAPI request fields, and documented pagination bounds against the running FastAPI app. Behavior is also covered by the PostgreSQL integration tests mapped in `tests/acceptance/backend_e2e_acceptance_matrix.md`, including ownership, revision conflicts, idempotency, state transitions, provenance and rollback.

## Explicit limitations

- This document does not establish a single end-to-end candidate journey; the acceptance matrix identifies that remaining gap.
- Live Firebase, SMTP, OCR/storage providers, external job sources and deployed worker/scheduler behavior require target-environment smoke evidence.
- The PRD and technical specification use different application lifecycle vocabularies. Until a product decision resolves that conflict, preserve the persisted states documented in `application-lifecycle.md`.
