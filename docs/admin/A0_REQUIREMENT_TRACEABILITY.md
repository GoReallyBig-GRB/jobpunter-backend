## Reading this register

- **Partial** means specific repository evidence exists, but one or more required acceptance paths remain unproven.
- **Not verified** means the available source/CI evidence does not establish the required behavior.
- **Policy open** means the governing specification leaves a decision unresolved; code must not silently choose a product/security policy.
- File and test references below are bounded source inspections through GitHub. They are not claims that local tests were run in this environment.
- PRD references refer to the user-provided *JobPunter PRD + Technical Spec v1.6*. That document incorporates the revised v1.3 architecture and explicitly preserves unresolved decisions. Do not interpret its historical section/version labels as proof that a decision is settled.

The decision record has been clarified. Still verify token/session expiry, revocation and step-up behavior where the spec leaves details open, and prove a second provider can be introduced without changing domain ownership or moving application data out of PostgreSQL.
2. Admin role/permission catalogue, privileged-grant approval, break-glass policy, last-admin/self-revocation rules, and support-intervention permissions.
3. Which configuration families require a second-person or separate approval before publication.
4. Initial production source set, permitted access methods, source-specific terms/rate limits, and licensed/API dependencies.
5. Hosting vendors and the exact production scheduler/worker topology.
6. Initial AI provider/model, credentials, and approved fallback behavior.
7. Data export scope, approval, retention, and audit policy.
8. Audit retention/review/export policy, alert thresholds and operational owners.

## User clarification and identity portability correction (2026-10-28)

The product decision is explicit: **Firebase is used for authentication only as a replaceable adapter; it does not lock the application to Firebase. PostgreSQL is the authoritative application database.** The older Firebase MVP record describes the current implementation, not an immutable product decision. Remove the earlier “identity decision conflict” classification; the remaining work is to verify that the anti-lock boundary is implemented and testable.

Source evidence:
- `app/ports/identity/__init__.py` defines the provider-neutral `IdentityProvider` contract.
- `app/api/deps.py` selects the configured provider at the backend trust boundary and fails closed for unsupported names.
- `app/infrastructure/identity/firebase.py` contains Firebase-specific token verification and provider-subject mapping.
- `app/infrastructure/db/models/identity.py` persists the provider/subject mapping to an internal user in PostgreSQL.
- `app/config/settings.py` and `app/infrastructure/db/session.py` configure PostgreSQL-backed application persistence.

**Implementation boundary:** only the Firebase adapter is currently implemented. The interface reduces coupling but does not mean a second provider can be enabled without code, identity-link/migration work, and verification. Add a provider-switch contract test (or a second test adapter) proving candidate, job, evaluation, Punt, application, configuration and audit records remain keyed to internal PostgreSQL identities rather than Firebase UIDs. Keep live Firebase sign-in and production runtime verification in the separate runtime gate.
