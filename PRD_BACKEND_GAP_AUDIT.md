# JobPunter Backend PRD Gap Audit

**Baseline:** JobPunter Product Requirements Document (PRD) + Technical Spec v1.4  
**Repository:** GoReallyBig-GRB/jobpunter-backend  
**Audit status:** Updated against `integration/backend-consolidation` after backend foundation, acquisition-persistence, governance, and canonicalization work. This supplements, and does not replace, the PRD's existing Current-State Audit & Gap Closure Control Register and invariant list.

## Status meanings

- **Partial:** a scaffold or only part of the required path exists.
- **Not implemented:** no implementation was found in the audited backend tree.
- **Not verified:** code exists but persistence, security, integration, or runtime evidence is missing.
- **Verified:** the complete required path exists and relevant tests pass.

A model, service file, route, screen, or green unit-test run alone does not prove a capability is implemented.

## Executive finding

The backend is an early foundation, not a complete MVP backend. The repository now has a linear Alembic history, ORM/database schema parity checks, candidate/identity/evidence persistence, a more reliable acquisition-persistence slice, and admin configuration lifecycle integration coverage. The latest completed CI run ([workflow run](https://github.com/GoReallyBig-GRB/jobpunter-backend/actions/runs/38065350335)) passed compilation, migration upgrade, ORM/schema parity, and the PostgreSQL 16 test suite: 428 tests passed, with one deprecation warning. Greenhouse acquisition integration tests cover durable run/raw-record/outbox persistence, audit attribution, authorization, invalid board-token rejection, idempotent run-key replay without refetching, and sanitized upstream-failure persistence/audit. Firebase unit tests verify expected-project initialization, rejection of a mismatched default app, revocation checking, and fail-closed handling of malformed decoded claims. PostgreSQL failure-injection tests verify candidate profile/source/evidence creation rolls back atomically and candidate claim/link creation does not leave partial records. AI governance tests also verify that successive executions use and record the respective current published configuration versions. PostgreSQL regressions cover duplicate delivery through the production canonicalization outbox handler and deterministic rejection of a candidate claim whose asserted years conflict with approved evidence. Admin governance validation also rejects task configuration keys that do not match a registered AI task. This run includes centralized server-owned AI task policy metadata and registry coverage tests, strict JSON-mode parsing including rejection of non-standard JSON constants and scalar root values, published-task configuration/traceability including config changes between executions, and persisted AI failure-category regressions; it does not establish full task input/output schema or semantic validation. This run includes concurrent canonicalization, concurrent first-time Punt qualification, Firebase project-bound/revocation-checked verifier behavior, identity persistence/concurrency and invalid-token non-creation, concurrent acquisition run-key idempotency, acquisition connector/persistence failure handling, deterministic hard-blocker enforcement, application lifecycle rollback/revision/audit/concurrency regressions, and candidate claim approval tests for ownership, expired/future-effective evidence, and concurrent revision safety. CI validates the tested paths only; it does not establish full PRD parity or production readiness. See [foundation migration and audit PR](https://github.com/GoReallyBig-GRB/jobpunter-backend/pull/2) and [acquisition reliability PR](https://github.com/GoReallyBig-GRB/jobpunter-backend/pull/3).

The remaining implementation gap is still substantial. Candidate-scoped evaluation listing, Punt qualification/persistence, application lifecycle transitions, lifecycle events, and outbox dispatch/canonicalization handling now exist as foundations. One Greenhouse public-board connector and a protected synchronous acquisition API now exist, but live-board verification, source registry CRUD/health management, worker deployment, an evaluation-generation engine, application packages, provider-neutral AI orchestration, scheduling, and integrations remain incomplete. A protected admin API now provides grant-checked telemetry/audit reads, versioned configuration draft/publish/rollback-draft operations, and an audited administrator-grant lifecycle. AI task configuration keys are checked against the canonical task registry, so administrators cannot publish a configuration for an unregistered task ID. PostgreSQL lifecycle tests cover draft/version sequencing, publish/retire behavior, rollback-draft creation, audit request IDs, grant creation/revocation/reactivation, and concurrent revocation safety. The first-admin bootstrap runbook exists but has not been exercised in staging; broader operational governance remains open.

## Priority implementation order

### P0: integrity and security

1. **Migration integrity is addressed for the current schema.** Keep the PostgreSQL migration and ORM-parity checks required on every schema change.
2. **Partially addressed.** Server-side ownership is enforced for implemented candidate APIs, with cross-candidate tests for evidence, evaluation, Punt and application resources. Firebase UID-to-account mapping and concurrent first sign-in have PostgreSQL coverage using injected verified claims; actual Firebase Admin token verification with production credentials and broader private-resource coverage remain open. Request-body user IDs must never establish ownership.
3. **Partially addressed.** Selected PostgreSQL tests now cover canonicalization/Punt convergence, identity creation races, acquisition rollback, invalid lifecycle transitions and concurrent application revision conflicts. Repository-wide transaction boundaries, rollback, uniqueness and idempotency coverage remain open.
4. **Implemented for the tested acquisition paths.** PostgreSQL tests verify connector failure persists a sanitized FAILED run and a mid-batch persistence failure rolls back raw records and outbox events while leaving the run FAILED. Real connectors, partial-source failures and worker recovery remain open.
5. **Partially addressed.** Deterministic hard-blocker enforcement is covered by PostgreSQL regression tests. Candidate claim APIs now require current approved evidence that matches each stated scalar claim fact before approval and reject cross-candidate evidence links. Admin grant lifecycle is now audited and self-elevation is blocked; initial first-admin bootstrap and its recovery procedure remain operator-managed and unverified. Broader hard-constraint coverage, semantic entailment beyond exact fact matching, and AI-generated claim validation remain open.
6. **Partially addressed for the implemented application lifecycle.** PostgreSQL tests verify invalid transitions do not mutate state or append events, stale revisions do not create duplicate events, concurrent transitions yield one winner, and SUBMITTED events carry a CANDIDATE actor. Broader event sources and verified integrations remain open.

### P1: complete the core workflow

1. A Greenhouse public-board connector and protected synchronous acquisition endpoint now connect a configured board to the durable run/raw-record/outbox pipeline. Source CRUD/health administration, live-board smoke testing and source-specific policy review remain open.
2. Normalize/split → retrieve/validate JD → completeness/freshness → resolve identity → canonical Job/version → provenance.
3. Connect the raw-record outbox event to a durable, idempotent worker with bounded retries and recovery.
4. Candidate profile/preferences/approved pathway/evidence → requirement matching → deterministic blockers → versioned explainable evaluation.
5. Evaluation → Punt qualification → candidate choice → application/package → candidate-recorded submission → auditable application lifecycle.
6. Provider-neutral AI task/version/configuration/execution records and evidence-grounded output validation.

### P2: remaining MVP capabilities and hardening

1. Document import/review and private artifact storage.
2. CV Studio, package editing/versioning and DOCX/PDF output.
3. Integration consent, scopes, connection health and revocation.
4. Protected admin configuration lifecycle, rollback and audit.
5. Notifications, operational logs/metrics, security regression tests and deployment/recovery runbooks.

## Audit rules

- The PRD v1.4 and its existing Current-State Audit & Gap Closure Control Register remain authoritative.
- Do not mark a capability complete because a model, screen, route or stub exists.
- Every schema change needs a migration, ORM update, repository review, tests and invariant verification.
- Assess source access, terms, authentication, rate limits and retention before implementing each production connector.
- Do not make paid services or separate infrastructure architectural prerequisites without demonstrated need.
- Keep unresolved hosting, identity, object storage, AI provider and initial source choices open until decided.
